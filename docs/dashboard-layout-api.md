# Dashboard layout API (Dev Preview)

`/api/couchmate/v2/client/dashboard-layout` uses the existing paired-client bearer token. GET is available to every paired client. PUT requires the explicitly approved `dashboard:write` capability; existing `configuration:write` grants are also accepted. The narrow dashboard capability does not grant access to profile assignment, settings replacement, backgrounds, or admin routes.

## Read

GET returns HTTP 200 with `Cache-Control: no-store`:

```json
{
  "revision": 42,
  "profile_id": "default",
  "room_order": ["43815954-f214-5030-8eae-bf16b163f97d"],
  "widget_orders": {
    "43815954-f214-5030-8eae-bf16b163f97d": ["aggregate|light", "aggregate|climate", "entity|cover.living_room"]
  }
}
```

Room and widget IDs are opaque, stable strings generated by the client. tvOS uses aggregate IDs such as `aggregate|light` and `aggregate|climate`, and entity tile IDs such as `entity|cover.living_room`. The Core does not infer identity from display names, resolve these IDs as Home Assistant entities, or change entity authorization. Room UUIDs are lowercased by tvOS. IDs must be nonempty, unique within each order, at most 256 characters, without surrounding whitespace or control characters. Each order supports at most 2048 IDs, with at most 256 room entries in `widget_orders`. Existing configuration document size and depth limits also apply.

An empty profile starts with `room_order: []` and `widget_orders: {}`. Clients apply known IDs in stored order, ignore unknown or removed tiles, and append newly available tiles in their normal order. Retaining unknown IDs on the server lets different client versions and temporary device availability share a layout without destructive pruning.

## Change one order

PUT takes the revision returned by GET, the profile ID, and exactly one order:

```json
{
  "base_revision": 42,
  "profile_id": "default",
  "scope": "rooms",
  "order": ["43815954-f214-5030-8eae-bf16b163f97d"]
}
```

For widgets, use `scope: "widgets"` and add `room_id`. Only this room's widget order changes. Other rooms, the room order, home settings, profile settings, and private background metadata are preserved. An empty widget order removes that room's override. An empty room order restores the default room ordering. `base_revision`, `scope`, and `order` are required; `room_id` is required only for widgets. `profile_id` is accepted as an additional guard and clients should always send it. Unsupported request keys are rejected.

Successful PUT returns HTTP 200 with the complete current layout in the same shape as GET. Saving an identical order does not increment revisions. A changed order is persisted atomically through the existing Home Assistant configuration Store and increments the assigned profile revision and global configuration revision. The layout is a reserved sibling of profile `settings`, so older clients replacing settings cannot erase it. Copying a profile also copies its layout.

## Conflicts and synchronization

`revision` is the global configuration revision, covering profile assignments as well as layout edits. Concurrent changes return HTTP 409:

```json
{
  "error": "revision_conflict",
  "current_revision": 43,
  "layout": {
    "revision": 43,
    "profile_id": "default",
    "room_order": [],
    "widget_orders": {}
  }
}
```

The response also includes a diagnostic `message`. A mismatching `profile_id` returns the same conflict response, even when its revision matches. Clients may reapply only the user's changed order against the latest revision, preserving every other scope. On a profile change, tvOS parks the previous profile's pending edits in that profile's cache and loads the newly assigned profile's cache. Those edits resume only if the client returns to their original profile. Never rebase them into the newly assigned profile.

Other Apple TVs observe saved layouts through GET polling every five seconds while the dashboard is active, and on reconnect. The normal configuration ETag and sync token change with layout writes as well; no websocket event is added. tvOS caches confirmed layouts and queued offline edits separately for each Core connection, paired client, and profile, then resynchronizes when connected. An old Core returns 404/405; clients must preserve their default layout and indicate that synchronization is unavailable.

Other errors: HTTP 400 for malformed input, 401 for an invalid/missing client token, and 403 with `error: "capability_required"` and `capability: "dashboard:write"` when the paired client lacks write permission.

## Aktueller tvOS-Hero (1.1, Build 9)

Geräte werden per langem Druck auf die Auswahltaste an der fokussierten Kachel
angeordnet. Es gibt keinen separaten Anordnen-Bereich im Hero. Die App verwendet
`scope: "widgets"`, `room_id: "hero|<Home-Assistant-area_id>"` und unveränderte
Entitäts-IDs, zum Beispiel `light.ceiling`. Zwei Gerätespalten und Kartengrößen
sind Darstellungseigenschaften der App, keine Änderung des Core-Datenformats.

Kartengrößen bleiben lokal auf dem Apple TV. Die bisherige Companion liest und
bearbeitet weiterhin `settings.companion.hero_entity_order`. Dieser Auswahlbereich
wird durch den neuen Reihenfolge-Endpunkt nicht überschrieben; die Companion
spiegelt den TV-Reihenfolge-Override noch nicht. Das erfordert eine gesonderte
Client-Anpassung, keine automatische Erweiterung von Gerätefreigaben im Core.

Core 1.4.0-beta.12 enthält die Layout-Schnittstelle. Nach Installation ist ein
vollständiger Home-Assistant-Neustart erforderlich. Bestehende Kopplungen erhalten
keine zusätzlichen Rechte automatisch: Ohne `dashboard:write` oder
`configuration:write` erneut koppeln und die Schreibfreigabe bestätigen.
